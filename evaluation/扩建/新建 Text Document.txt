项目内 Python 文件用途如下。

- `__init__.py`：不是包初始化文件，而是一个独立脚本；第 12 行有语法错误，当前不参与应用运行。
- `src/gui/main_window.py`：系统主编排器。把爬虫、NLP、数据库导入、可视化、Agent 对话全部串到 GUI 标签页中。
- `src/crawler/spider.py`：当前唯一数据摄取入口，从中文维基百科抓取页面 HTML 与兼容文本。
- `src/nlp/nlp_pipeline.py`：当前唯一 NLP 批处理入口，处理 `data/raw_json/*.json`。

- `src/nlp/triple_builder.py`：三元组与叙事块去重、合并、落盘。
- `src/nlp/text_normalizer.py`：用 OpenCC 做简繁统一。
- `src/knowledge_graph/neo4j_loader.py`：把 `*_triples.json` 导入 Neo4j。
- `src/vector_store/chroma_store.py`：把 `*_narratives.json` 导入 Chroma，并执行语义检索。
- `src/agent/llm_agent.py`：执行 Neo4j 检索、Chroma 检索、构造提示词、调用 Ollama 或 OpenAI 兼容接口。
- `src/visualization/app.py`：从 Neo4j 读图，暴露 `/api/graph`，前端用 D3 渲染。

- `src/gui/i18n.py`：中英文本资源。
- `src/gui/theme_manager.py`、`window_customization.py`、`console_manager.py`：纯 GUI/Windows 支撑模块。
- `src/nlp/entity_extractor.py`、`relation_extractor.py`、`segmenter.py`、`html_parser.py`、`infobox_extractor.py`、`narrative_processor.py`：都存在于仓库中，但从当前主流程调用关系看，没有进入现在的 `preprocess_v2` 主链。

# Architecture Overview

这是一个典型的“本地知识库 + 本地/远程 LLM + GUI”项目，主架构是五段式：

1. 数据摄取：[`src/crawler/spider.py`](</F:/第二次托洛洛测试 -重大进展/src/crawler/spider.py>)
2. 知识抽取：[`src/nlp/preprocess.py`](</F:/第二次托洛洛测试 -重大进展/src/nlp/preprocess.py>) + [`src/nlp/nlp_pipeline.py`](</F:/第二次托洛洛测试 -重大进展/src/nlp/nlp_pipeline.py>)
3. 存储落地：Neo4j + Chroma
4. 检索增强：[`src/agent/llm_agent.py`](</F:/第二次托洛洛测试 -重大进展/src/agent/llm_agent.py>)
5. 交互层：[`src/gui/main_window.py`](</F:/第二次托洛洛测试 -重大进展/src/gui/main_window.py>) + [`src/visualization/app.py`](</F:/第二次托洛洛测试 -重大进展/src/visualization/app.py>)

当前主流程是 GUI 驱动的，而不是 CLI 驱动的。`main.py` 启动后直接进入 GUI，所有核心操作都通过标签页触发：

- 爬虫标签页调用 `TololoCrawler.crawl_all()`
- NLP 标签页调用 `NlpPipeline.process_all()`
- 数据库标签页分别调用 `Neo4jLoader.load_all_triples()` 和 `ChromaStore.load_all_narratives()`
- Agent 标签页调用 `LLMAgent.search_*()` 与 `LLMAgent.chat()`
- 可视化标签页在同一进程内启动 Flask 图服务

当前实际在跑的知识抽取链是 `preprocess_v2`，`data/triples/summary.json` 也明确记录了 `pipeline: "preprocess_v2"`。

# Data Pipeline

当前数据处理流程完全可以从代码里串起来：

`zh.wikipedia.org/wiki/{title}` 页面  
→ `TololoCrawler.get_html_content()` 抓取正文 DOM  
→ 保存到 `data/raw_json/*_html.json`  
→ `NlpPipeline.process_all()` 批处理这些 JSON  
→ `WikiPreprocessor.process_json_data()` 做 HTML 清洗和结构抽取  
→ 生成 `all_triples` 与 `embedding_chunks`  
→ `TripleBuilder` 去重并落盘  
→ 输出 `data/triples/*_triples.json` 和 `data/triples/*_narratives.json`

当前摄取 pipeline 的关键事实：

- 数据源是中文维基百科 HTML 页面，不是 MediaWiki API。
- 入口页面是“太阳系”，再从其中自动发现更多天文相关链接。
- 抓取结果同时保存 `html` 和 `raw_text/text`，但当前结构化抽取主输入是 `html`，不是 `text`。
- 抽取时会移除 `navbox/references/toc/hatnote/metadata` 等噪音 DOM。
- 章节切分依据真实 HTML 标题层级 `h1/h2/h3`，不是纯文本启发式。
- 三元组抽取完全基于规则与固定 ontology，不调用 LLM。
- 向量入库的原料不是整页，而是按 section 切成 120 到 800 字左右的 chunk。
- 当前仓库数据规模是：
  - `482` 个 `raw_json` 页面文件
  - `444` 个三元组文件
  - `569` 个叙事文件
  - `summary.json` 记录最近一次主流程处理了 `474` 个文件，产出 `587` 个三元组、`3193` 个叙事块

当前知识抽取方法判断如下。

- `Regex`：是，且是主方法。`preprocess.py` 的 `TEXT_RULES` 是当前正文关系抽取核心。
- `NER`：否。没有 spaCy/stanza/transformers 这类 NER 组件进入主流程。
- `LLM extraction`：否。`preprocess.py` 文件头也明确写了“不调用 LLM”。
- `Rule-based extraction`：是，主方法就是 rule-based + ontology 约束。

# Retrieval Pipeline

当前检索是“双检索 + 组装提示词”的 RAG 结构：

用户问题  
→ `LLMAgent.search_neo4j()`  
→ `LLMAgent.search_chroma()`  
→ 结果拼成 system prompt  
→ `LLMAgent.chat()` 调模型生成回答

图检索链路：

- Neo4j 数据来自 `data/triples/*_triples.json`
- `Neo4jLoader` 导入时：
  - 非数值 object：建节点 + 建关系
  - 数值 object：不建 object 节点，而是写成 subject 节点属性
- 在线查询时执行的是单条 Cypher：
  - `MATCH (n)-[r]->(m) WHERE n.name CONTAINS $kw OR m.name CONTAINS $kw RETURN ...`
- 这是单跳边检索，不是多跳图遍历

向量检索链路：

- Chroma 数据来自 `data/triples/*_narratives.json`
- `ChromaStore` 当前使用 `LocalHashEmbedder`
- 向量不是外部 embedding API，也不是 sentence-transformers；是本地 `HashingVectorizer` 的字符 2-4 gram 哈希向量，维度 `2048`
- 检索时用 `collection.query(query_embeddings=..., n_results=top_k)`

数据库不可用时的兜底检索：

- Neo4j 不可用时，回退到遍历本地 `*_triples.json` 做关键词打分
- Chroma 不可用时，回退到遍历本地 `*_narratives.json` 做关键词打分

当前检索方式判断如下。

- `Neo4j query`：是
- `SQLite`：间接是。Chroma 持久化底层就是 SQLite，但业务代码不直接用 SQL 做问答检索
- `Chroma similarity search`：是
- `FAISS`：否
- `BM25`：否。Chroma schema 里有 sparse/bm25 配置位，但当前业务代码没有启用
- `Reranker`：否
- `Graph traversal`：严格说不是完整图遍历，只是单跳关系匹配

当前数据库结构如下。

- Neo4j 节点标签由 `Neo4jLoader._infer_label()` 推断，候选包括 `Planet/Star/Nebula/Galaxy/Asteroid/Comet/Satellite/DwarfPlanet/Mission/CelestialBody/Entity/Concept/PlanetType/OrbitParameter/EnvironmentalFeature`
- 节点核心属性是 `name`
- 关系类型直接使用三元组里的 `relation`
- 数值型事实不会形成关系边，而会写成节点属性

当前向量数据库结构如下。

- Chroma collection 名称：`astronomy_narratives`
- 维度：`2048`
- 当前 SQLite 里有 `4173` 条 embeddings
- collection 有两个 segment：
  - `VECTOR`：`hnsw-local-persisted`
  - `METADATA`：`sqlite`
- 元数据字段已实际落库的有：
  - `page_title`
  - `section`
  - `source`
  - `keywords`
  - `chroma:document`
- `schema_str` 显示：
  - `#document` 开启了 FTS
  - `#embedding` 开启了 HNSW 向量索引
  - `page_title/section/source/keywords` 开启了字符串倒排索引

# LLM Pipeline

当前模型调用有两条分支：

- 本地分支：Ollama
- 远程分支：OpenAI 兼容 API

本地分支事实：

- 健康检查：`GET /api/tags`
- 模型存在检查：`GET /api/tags`
- 对话生成：`POST /api/chat`
- 流式协议：Ollama NDJSON
- 默认模型：`qwen3:4b`
- 默认模型目录环境变量：`OLLAMA_MODELS=models/ollama`

远程分支事实：

- 由 `settings.json -> llm_source.use_remote_api` 控制
- 接口地址格式：`{api_base}/chat/completions`
- 鉴权：`Authorization: Bearer {api_key}`
- 流式协议：OpenAI SSE
- 代码兼容 OpenAI 风格 `choices[0].message.content` / `delta.content`

当前 Agent 工作流程如下。

1. GUI AgentTab 接收用户输入
2. 创建 `LLMAgent`
3. 先做状态检测
4. 调 `search_neo4j(query)`
5. 调 `search_chroma(query)`
6. 把两类结果显示到检索详情面板
7. 用检索结果拼接 system prompt
8. 调 `chat()`
9. 流式回显 token
10. 把问答历史保存在内存 `chat_history` 中，默认只保留最近 10 轮

当前使用的大模型接口判断如下。

- `Ollama`：是，当前默认主接口
- `OpenAI official SDK`：否，没有 `openai` 包调用
- `OpenAI-compatible HTTP API`：是，自己用 `urllib` 直连
- `Transformers / local HF model`：否

当前对你点名的技术使用情况如下。

- `BeautifulSoup`：仍在使用，`src/crawler/spider.py`、`src/nlp/preprocess.py`
- `Scrapy`：未使用
- `Requests`：仍在使用，`src/crawler/spider.py`
- `Playwright`：未使用
- `Selenium`：未使用
- `MediaWiki API`：未使用
- `Wikidata API`：未使用
- `JSON API`：用于 LLM 服务接口，Ollama 和 OpenAI-compatible；不用于百科内容抓取

# Possible Architecture Problems

当前最大的架构问题，是“存在两套并行但不一致的系统真相”：主流程已经切到 `preprocess_v2`，但仓库里仍保留一整套旧 NLP 组件、另一套配置入口，以及一些不会进入当前热路径的逻辑，导致配置、数据模型和实际执行路径分裂。

更具体地说，当前最值得注意的问题有这些：

- `settings.json` 和 `config.py` 存在配置漂移。LLMAgent 会读 `settings.json`，但 `Neo4jLoader`、`ChromaStore`、`visualization.app`、爬虫与多数数据模块仍直接读 `config.py`。这意味着 GUI 设置里改了连接参数，不一定会真正影响所有运行模块。
- Agent 远程 API 分支与 GUI 状态检查不一致。`LLMAgent.chat()` 支持远程 OpenAI-compatible API，但 `AgentTab._ask_llm()` 在发问前仍强制检查本地 Ollama 是否运行、模型是否已下载，所以“启用远程 API”在 GUI 层并不真正独立。
- Neo4j 的数值事实被写成节点属性而不是关系边，但在线检索只查 `MATCH (n)-[r]->(m)`。结果是大量 `HAS_MASS/HAS_RADIUS` 之类数值知识即使已入 Neo4j，也不会被 `search_neo4j()` 命中。
- 向量检索与命名预期不一致。`ChromaStore` 里有 `model_name='paraphrase-multilingual-MiniLM-L12-v2'`，但实际完全没用这个模型，而是用了离线 `HashingVectorizer`。这能离线运行，但语义检索能力会明显弱于真实 embedding 模型。
- 图 schema 比较松散。Neo4j 节点标签由 `_infer_label()` 通过名字关键词临时推断，不是从抽取阶段稳定传递；很多实体最终会落到 `CelestialBody` 这类粗粒度标签。
- 仓库中有一批未进入主流程的 NLP 模块，说明系统还处在“旧链路未清理、新链路已上线”的过渡态。长期看会提高维护成本，也会让后续分析和调试更难。
- 根目录 `__init__.py` 当前有语法错误，虽然不影响主 GUI 路径，但说明仓库里存在未收敛的非主线脚本状态。
